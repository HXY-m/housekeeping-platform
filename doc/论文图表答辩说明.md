# 论文图表答辩说明

> 适用场景：老师根据论文中的系统架构图、功能模块图、用例图、ER 图、流程图、时序图等非系统截图进行提问。  
> 准备目标：不只是知道“图里有什么”，还要能说清楚“为什么这样设计”和“它对应到系统哪里”。

---

## 一、图表答辩的通用回答方法

老师问图的时候，建议你按这个顺序回答：

1. 先说这张图表达的对象  
2. 再说图中有哪些核心元素  
3. 然后说元素之间是什么关系  
4. 最后说它对应到系统中的哪些功能或代码

可以直接套用这句话：

这张图主要说明系统中某个业务或结构的整体关系。图中的核心对象包括用户、服务人员、管理员以及相关业务数据，箭头或关联线表示它们之间的调用、流转或数据关系。它在系统中对应的是前端页面、后端接口、业务服务和数据库表之间的配合。

## 二、系统总体架构图

### 老师可能问什么

- 这张架构图为什么这样分层？
- 前后端分离体现在哪里？
- Spring Boot、Vue、MySQL 分别承担什么职责？
- 为什么采用 B/S 架构？

### 推荐回答

这张图主要展示系统的总体技术架构。系统采用 B/S 架构和前后端分离模式，用户通过浏览器访问 Vue 前端页面，前端通过 HTTP 请求调用后端 Spring Boot 接口，后端再通过 MyBatis-Plus 访问 MySQL 数据库。

前端主要负责页面展示、表单交互、路由跳转和数据可视化；后端主要负责身份认证、权限校验、业务规则处理和数据持久化；数据库主要保存用户、角色、服务项目、服务人员档案、订单、支付、售后、通知等业务数据。

## 五、ER 图

### 老师可能问什么

- ER 图里有哪些核心实体？
- 用户表和服务人员表是什么关系？
- 订单表和其他表有什么关系？
- 为什么要单独设计角色表和权限表？
- 为什么附件、支付记录、服务记录要单独建表？

### 推荐回答

ER 图主要展示系统数据库中核心实体之间的关系。系统核心实体包括用户、角色、权限、服务项目、服务人员档案、资质申请、订单、支付记录、服务过程记录、评价、售后工单、消息通知和操作日志。

用户表保存基础账号信息；角色和权限表用于实现 RBAC 权限控制；服务人员档案表用于保存服务人员的服务能力、资质状态和展示信息；订单表连接普通用户、服务人员和服务项目，是系统业务主线；支付记录、服务记录、售后和通知表则围绕订单扩展，保证业务过程可追踪。

### 重点关系

用户与角色：多对多关系，通过用户角色关系表维护。  
角色与权限：多对多关系，通过角色权限关系表维护。  
用户与地址：一对多关系，一个用户可以有多个地址。  
用户与服务人员档案：一对一或一对零关系，普通用户不一定有服务人员档案。  
订单与支付记录：一对多关系，一个订单可以有支付流水记录。  
订单与服务过程记录：一对多关系，一个订单可以上传多条过程记录。  
订单与售后：一对多关系，一个订单可能产生售后反馈。

- 用户实体：[SysUserEntity.java](F:\Desktop\demo\project\housekeeping\backend\housekeeping-server\src\main\java\com\housekeeping\auth\entity\SysUserEntity.java)
- 服务人员实体：[WorkerEntity.java](F:\Desktop\demo\project\housekeeping\backend\housekeeping-server\src\main\java\com\housekeeping\worker\entity\WorkerEntity.java)

如果老师问“为什么不把所有信息都放在订单表里”，可以答：订单表只保存订单主信息，支付、服务过程、售后、附件等属于可扩展信息，单独建表可以减少主表冗余，也便于一对多记录和后期扩展。

## 六、订单状态流程图

### 老师可能问什么

- 订单状态为什么这么设计？
- 用户和服务人员分别在什么时候操作？
- 为什么不是服务人员单方面推进？
- 支付和订单状态有什么关系？

### 推荐回答

订单状态流程图体现的是订单从创建到完成的全过程。系统中的主要状态包括：待接单、已接单、待用户确认、服务中、待用户确认完工和已完成。

用户下单后订单进入待接单状态；服务人员接单后进入已接单；用户支付并确认预约后进入待上门或已确认安排；服务人员开始服务后进入服务中；服务人员提交完工后进入待用户确认完工；用户确认后订单才最终完成。

这样设计的目的是让订单由用户和服务人员共同推进，避免单方面修改状态，更符合真实家政服务场景。

- 用户订单页面：[OrdersView.vue](F:\Desktop\demo\project\housekeeping\frontend\web\src\views\consumer\OrdersView.vue)

如果老师问“如果状态不合法怎么办”，可以答：后端在每次状态变更前都会校验当前状态，例如用户确认预约前必须是服务人员已接单，并且订单必须已支付，否则后端会抛出业务异常。

## 七、预约下单流程图

### 老师可能问什么

- 用户预约下单的流程是什么？
- 可预约时段怎么计算？
- 如何避免重复预约？
- 前端校验和后端校验有什么区别？

### 推荐回答

预约下单流程从用户选择服务人员开始。用户进入预约页面后，选择服务日期，系统调用后端接口查询该服务人员当前日期下的可预约时段。用户选择地址和时间后提交订单，后端再次校验服务人员资质、服务范围和时段是否可用，确认无误后创建订单。

系统避免重复预约的核心在后端。前端只负责展示可选项，后端在创建订单前会再次检查同一服务人员、同一日期、同一时段是否已经存在未完成订单。

- 为什么需要售后模块？
- 管理员处理后用户怎么知道？

### 推荐回答

售后流程主要包括用户发起售后、上传凭证、管理员查看并处理、系统记录处理结果并通知用户。家政服务是线下履约场景，服务质量可能存在争议，所以售后模块用于保证用户反馈有入口、平台处理有记录、处理结果可追踪。

系统在管理员处理售后时会判断当前工单状态，如果已经是最终状态，就不允许重复处理。处理完成后还会写入操作日志并发送站内通知给用户。

## 十二、最后的背诵重点

答辩前你至少要记住这 5 句话：

1. 架构图讲的是前后端分离和 B/S 架构。  
2. 功能模块图讲的是六大核心模块。  
3. ER 图讲的是用户、角色、服务人员、订单、支付、售后等核心数据关系。  
4. 订单流程图讲的是用户和服务人员共同推进订单状态。  
5. 时序图讲的是前端、后端业务层和数据库之间按时间顺序交互。

老师问图的时候，千万不要只说图上有什么，要尽量把它和“系统功能、数据库、代码位置”连起来讲。
